# Deploying WeaboTalk (Render + Supabase)

WeaboTalk runs on **Render** as a Docker web service. **Supabase** provides the
Postgres database and the storage for uploaded images.

| Part | Where | Notes |
|---|---|---|
| Rails app (Puma behind Thruster) | Render web service | Built from `Dockerfile`, configured by `render.yaml` |
| Database | Supabase Postgres | One database; tables are created automatically on boot |
| Uploaded images (avatars, banners, post images) | Supabase Storage | Through Supabase's S3-compatible API |
| Real-time notifications | Solid Cable | Stored in the same Supabase database, no Redis needed |
| Background jobs (emails, notification broadcasts) | Inside the web process | Rails' default `async` adapter |

---

## 1. Supabase

### 1.1 Create the project

1. Create a project at [supabase.com](https://supabase.com).
2. Pick a region close to your users. You'll use the matching Render region later.
   For example, Supabase `ap-southeast-1` (Singapore) pairs with Render `singapore`.
3. Save the database password somewhere safe.

### 1.2 Database connection string → `DATABASE_URL`

1. In your project, click **Connect**.
2. Copy the **Session pooler** connection string. It looks like:
   `postgresql://postgres.<project-ref>:<password>@aws-0-<region>.pooler.supabase.com:5432/postgres`
3. Replace `[YOUR-PASSWORD]` with your database password.

Use the **Session pooler**, not the direct connection. Supabase's direct
connection is IPv6-only, and Render connects over IPv4.

### 1.3 Storage → `SUPABASE_S3_*`

1. Go to **Storage** and create a bucket, for example `uploads`.
   Keep it **private**: Rails serves images through short-lived signed URLs.
2. Go to **Project Settings → Storage → S3 Connection**:
   - Copy the **Endpoint** → `SUPABASE_S3_ENDPOINT`
     (like `https://<project-ref>.storage.supabase.co/storage/v1/s3`)
   - Copy the **Region** → `SUPABASE_S3_REGION` (like `ap-southeast-1`)
3. Under **S3 Access Keys**, create a new key:
   - **Access key ID** → `SUPABASE_S3_ACCESS_KEY_ID`
   - **Secret access key** → `SUPABASE_S3_SECRET_ACCESS_KEY`. It's shown only once.
4. The bucket name → `SUPABASE_S3_BUCKET`

## 2. Email (SMTP)

Sign-up needs email confirmation, so production needs a working SMTP server.
With Gmail:

| Variable | Value |
|---|---|
| `SMTP_ADDRESS` | `smtp.gmail.com` |
| `SMTP_PORT` | `587` |
| `SMTP_USERNAME` | your Gmail address |
| `SMTP_PASSWORD` | a Gmail [App Password](https://myaccount.google.com/apppasswords) (not your normal password) |
| `MAIL_FROM` | the "from" address, usually the same Gmail address |

---

## 3. Render

1. Push the code to GitHub.
2. In Render, choose **New → Blueprint** and select the repository.
   Render reads `render.yaml` and creates the `weabo-talk` web service.
3. Render asks for every variable marked `sync: false`. Fill them in from
   sections 1 and 2. Leave `APP_HOST` empty for now.
4. Deploy. On first boot, `bin/docker-entrypoint` runs `bin/rails db:prepare`,
   which creates all tables in Supabase.
5. Copy your app's URL (like `weabo-talk.onrender.com`). Set `APP_HOST` to it
   **without** `https://`, then redeploy. Email links use it.
6. Open the URL and sign up to check that the confirmation email arrives.

`SECRET_KEY_BASE` is generated by Render automatically. `config/master.key` is
not needed: the app doesn't read encrypted credentials.

## 4. Environment variables

| Variable | Required | Example / source |
|---|---|---|
| `DATABASE_URL` | yes | Supabase Session pooler string (1.2) |
| `DB_PREPARED_STATEMENTS` | no | Set to `false` only if you use the **Transaction** pooler (port `6543`) |
| `SECRET_KEY_BASE` | yes | Generated by Render |
| `APP_HOST` | yes | `weabo-talk.onrender.com` |
| `APP_PROTOCOL` | yes | `https` (set in `render.yaml`) |
| `HTTP_PORT`, `PORT` | yes | `10000` (set in `render.yaml`) |
| `SUPABASE_S3_ENDPOINT` | yes | Supabase S3 Connection (1.3) |
| `SUPABASE_S3_REGION` | yes | Supabase S3 Connection (1.3) |
| `SUPABASE_S3_BUCKET` | yes | Your bucket name, e.g. `uploads` |
| `SUPABASE_S3_ACCESS_KEY_ID` | yes | Supabase S3 Access Keys (1.3) |
| `SUPABASE_S3_SECRET_ACCESS_KEY` | yes | Supabase S3 Access Keys (1.3) |
| `SMTP_ADDRESS`, `SMTP_PORT`, `SMTP_USERNAME`, `SMTP_PASSWORD` | yes | Section 2 |
| `MAIL_FROM` | yes | Section 2 |
| `RAILS_LOG_LEVEL` | no | `info` by default; `debug` for troubleshooting |

## 5. Things to know

- **Free Render services sleep** after about 15 minutes without traffic. The
  next visit takes around a minute while the app starts again.
- **Free Supabase projects pause** after a week without activity. Resume them
  from the Supabase dashboard.
- **Background jobs run in the web process.** If the app restarts while an
  email is queued, that email is lost. Users can request a new confirmation
  email from the sign-in page.
- **Real-time notifications** use Solid Cable, which checks the database for
  new messages every 0.1 seconds. Old messages are cleaned up after 1 day.

## 6. Troubleshooting

| Problem | Fix |
|---|---|
| `prepared statement "a1" already exists` | You're using the Transaction pooler (port `6543`). Switch to the Session pooler, or set `DB_PREPARED_STATEMENTS=false`. |
| Database connection times out | You're probably using the direct connection (IPv6). Use the Session pooler string. |
| Image upload fails with a checksum or signature error | Check that all `SUPABASE_S3_*` values are correct, and that the endpoint ends in `/storage/v1/s3`. |
| Confirmation emails don't arrive | Check the Render logs. Delivery errors are raised there. With Gmail, use an App Password. |
| Email links point to the wrong site | Set `APP_HOST` to your Render URL without `https://`. |
| Health check fails | Make sure `HTTP_PORT` and `PORT` are both `10000`. |
